Windows 端 UI 重构与真机验收支持。当日完成：截图驱动的样式根因定位、类 macOS 扁平视觉重做、竖版窗口、设置/主题入口拆分、测试版流水线。

## 当日结论

| 问题 | 结论 |
|---|---|
| 内容贴边、组件挤在一起 | **根因是 CSS 层叠**：`index.css` 中未分层的 `* { margin:0; padding:0 }` 等 reset 压过了 Tailwind v4 的 `@layer utilities`，全站间距/边框/字号工具类失效。修复后同类问题不再出现 |
| 设置按钮找不到 | 设置仍是图标按钮且形似主题切换。已拆为「主题切换（图标）」+「设置（纯文字）」 |
| 横版窗口不适合消息流 | 改为竖版，最终定稿 400×680（最小 340×420） |
| 视觉太像通用 AI 生成界面 | 改为类 macOS 扁平语言：白色内容面 + 细分割线 + 大留白，去卡片描边与阴影 |
| 标题/正文/渠道分层不清 | 三档字阶 + 渠道徽标；正文不再承担已读/未读表达 |

有效性验证手段（本项目可复用）：headless Chrome + CDP 取真实几何与计算样式、像素边界测量、Vision OCR 文本坐标。截图无法直接读取时，用它们定位布局问题比猜更快。

## 样式错位根因：未分层 CSS 覆盖 Tailwind 工具类

- [x] 实机截图（`screenshot/win-light-start.png`、`win-light-list.png`，1000×750 = 800×600@125%）逐像素量测：所有内容左边缘落在 `x=0`，而 `px-4`/`px-5` 应给出约 20–25px 内边距；`screenshot` 与本地 headless 渲染数值一致 → 非环境问题
- [x] 根因：`styles/index.css` 中的 `* { margin:0; padding:0; box-sizing:border-box }`、`button { ... }`、`input,select,textarea { ... }` 写在 layer 之外。Tailwind v4 把工具类放在 `@layer utilities`，**未分层样式无视优先级压过所有 layer**，于是全站 `px-*`/`py-*`/`m-*`/`space-y-*`/`border`/`text-*` 全部失效 —— 这也是最初「样式错位严重、样式丑陋」的真正原因
- [x] 修复：Token、`html/body/#root`、`body` 字体、`button` 指针、`:focus-visible`、`::selection`、搜索框清除按钮全部移入 `@layer base`；删除与 preflight 重复的 `*` reset 与表单控件重置；滚动条与 `prefers-reduced-motion` 保留不分层（不与工具类竞争）
- [x] 量化验证（headless Chrome `--force-device-scale-factor=1.25` + 自写像素测量与 Vision OCR）：引导页铃铛图标 `x=0 → x=165`（`max-w-xl` 居中 112px + `px-5` 25px）；设置页分区标题 `x=103`、字段 `x=119`；400×300 下内容左右各约 16px、按钮换行不裁切；右侧内容边界 834（与左侧 165 对称）
- [x] 新增 `?view=settings`（仅影响初始视图），便于浏览器预览核对设置页
- [x] 新增本地测量工具链（`/tmp` 内一次性脚本，未入库）：Chrome headless 截图 → 像素边界测量 → Vision OCR 文本与坐标
- [x] `docs/development-guide.md` 新增「7. 前端样式约定」：基样式必须进 `@layer base`、不得重复 preflight reset、主题只走语义 Token、浏览器预览必须 `isTauriRuntime()` 守卫
- [x] 本轮验证：`npm run typecheck` / `test`（26 项）/ `build` / `check:tauri-versions` 通过

## 2.0.1 第二次修订：macOS 外观不对的真正原因（链接 SDK）

用户反馈「还是有错位，而且感觉和以前样式不太一样」。用屏幕权限直接截图对比后定位到根因：

- [x] 证据一：安装的 `/Applications/Nexthrum.app`（2.0.1/2002）`DTSDKName = macosx14.5`、`DTXcode = 1540` —— CI 用 `macos-14` runner 构建，只带 macOS 14 SDK
- [x] 证据二：本机 Debug 构建（Xcode 27.1）`DTSDKName = macosx27.0`；同一窗口 837×512 下两者渲染不同：内容面 `rgb(251,251,251)` vs `rgb(255,255,255)`、侧边栏分界 `289px` vs `287px`、动作按钮位置均不同 —— 即旧 SDK 在 macOS 26/27 上退回旧外观
- [x] 结论：macOS 用「链接 SDK」决定外观。用 macOS 14 SDK 构建的 app 在 macOS 27 上永远是旧样式，所以「和以前不一样」并非代码改动，而是构建工具链
- [x] 修复一：macOS 发布 job 从 `macos-14` 切到 `macos-26`（顺带解决 `macos-14` 将于 2026-11-02 停止支持的问题）
- [x] 修复二：撤销 `.offset(x: -2)` 视觉补偿 —— 实测同一个 offset 在 SDK 14.5 下把标题从 `323` 挪到 `322`（对齐），在 SDK 27 下却让标题落到 `316~318` 而内容面是 `320`（反向偏移）。字形留白随 SDK 变化，不能用固定偏移硬凑
- [x] 文档：`docs/release.md` 新增「3.0 构建 SDK 决定外观」，写明 runner 要求、`DTSDKName` 校验方式与「不要用偏移量凑对齐」
- [x] 构建号再递增到 2003，重新发布 2.0.1

**实测对齐数据（安装版 2.0.1/2002，SDK 14.5，窗口 837×512 @2x）**：内容面左边缘 `322`、标题字形 `323`、搜索框 `322`、状态行文字 `323` —— 该构建其实已对齐；错位观感来自旧 SDK 的旧外观。
